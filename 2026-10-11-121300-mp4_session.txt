> why are we slicing off the first n rows after sorting?                        

● Because sorted(...) by itself returns the entire list rearranged in descending
  order — all 5 rows, not just the top ones. The spec only wants n of them, so
  we still need to cut it down after sorting.

  Walking through top_n(rows, "points", 2) on the sample data:

  1. sorted(records, key=lambda row: float(row["points"]), reverse=True)
     produces all 5 rows, reordered by points descending:
     [Eve(55), Dee(40), Cy(30), Ben(25), Ana(10)]
  2. [:2] then takes just the first 2 elements of that list: [Eve(55), Dee(40)]

  Without the slice, the function would return all 5 rows (sorted correctly, but
  ignoring n entirely) — the test asserts exactly ["Eve", "Dee"], so it'd fail
  with 5 names instead of 2.

  Slicing is the step that actually enforces "give me the top n"; sorting alone
  only establishes the order.

> and sorted is a function from what?                                           

● sorted() is a Python built-in function — part of the core language, no import
  needed (unlike csv or json, which we did have to import in load_records).

  A couple of related things worth knowing:

  - It's available globally in every Python program, right alongside things like
    len(), sum(), min(), max(), all() — all of which we've already used in this
    file.
  - It's distinct from list.sort(), which is a method on list objects.
    list.sort() sorts in place and returns None; sorted(x) takes any iterable
    (list, tuple, dict keys, generator, etc.) and returns a new list, leaving
    the original untouched. That's why top_n uses sorted() — we don't want to
    mutate the caller's records list as a side effect.
  - The key= and reverse= keyword arguments we're using are part of sorted()'s
    own signature, not something specific to our lambda.

  Ready to move on to to_report whenever you are, or happy to keep digging into
  sorted()/sort() differences if useful.
